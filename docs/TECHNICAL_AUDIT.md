# Forever — технический аудит

Дата аудита: 2026-11-26  
Проверенная версия: ветка `main`, файл `index.html` (2366 строк, около 135 KB).

## Краткий вывод

Forever — функциональный прототип мессенджера, реализованный как однофайловое веб-приложение. В текущем виде в нём уже предусмотрены авторизация Supabase, профили, контакты, личные и групповые чаты, каналы, реакции, настройки и мобильная навигация.

Проект не следует переписывать с нуля до проверки существующей базы данных и фактического поведения приложения. Рекомендуется поэтапная модернизация с сохранением текущих таблиц и пользовательских данных.

## Что обнаружено

### Структура и запуск

- Основная реализация находится в корневом `index.html`.
- Отдельного `package.json`, README с инструкциями, SQL-схемы или миграций в проверенных стандартных путях нет.
- Supabase JS подключается через CDN.
- CSS, HTML-разметка, локализация, состояние интерфейса и бизнес-логика смешаны в одном файле.
- Проверка проводилась статически по исходному коду; приложение не запускалось в браузере.

### Используемые таблицы Supabase

По запросам из клиента обнаружены:

- `forever_profiles`
- `forever_contacts`
- `forever_messages`
- `forever_channels`
- `forever_channel_members`
- `forever_channel_messages`
- `forever_groups`
- `forever_group_members`
- `forever_group_messages`
- `forever_reactions`

Точная структура таблиц, индексы, ограничения, триггеры и RLS-политики пока неизвестны. Нельзя считать клиентские проверки разрешений достаточной защитой.

### Приоритетные риски

1. **RLS и полномочия.** Клиентские функции бана и административные элементы интерфейса проверяют роль на стороне браузера. Необходимо проверить, что Supabase RLS запрещает обычному пользователю менять чужие профили, выдавать себе роль, удалять чужие данные или обходить ограничения через прямые API-запросы.
2. **Нет схемы и миграций в репозитории.** Разработка и восстановление проекта затруднены; неизвестно, какие ограничения и политики реально действуют в удалённой базе.
3. **Polling вместо Realtime.** Функция `tick()` запускается каждые пять секунд и отдельно опрашивает личные, групповые и канальные сообщения, а также запросы в контакты.
4. **Неатомарное удаление канала.** Сообщения, участники и канал удаляются тремя отдельными запросами. При частичном отказе остаётся неполное состояние.
5. **Непоследовательная обработка ошибок.** В нескольких функциях результаты запросов Supabase игнорируются; пользователю может показываться успешный результат, хотя операция не завершилась.
6. **Хрупкая генерация HTML.** Значительная часть интерфейса строится через `innerHTML` и шаблонные строки. Для пользовательских полей требуется последовательное экранирование и отказ от вставки непроверенных значений в атрибуты обработчиков.
7. **Сложность сопровождения.** Состояние приложения хранится в глобальных переменных; загрузка данных, отображение и навигация тесно связаны.

### Публичный ключ

В клиенте указан Supabase-ключ с ролью `anon`. Это публичный ключ для клиентского приложения, а не service-role ключ. Его присутствие в браузерном коде ожидаемо. Безопасность данных должна обеспечиваться RLS и ограничениями на стороне базы.

## Что требуется для безопасного продолжения

| Таблица | RLS |
|---|---|
| forever_profiles | включён |
| forever_messages | включён |
| forever_contacts | включён |
| forever_channels | включён |

У четырёх таблиц Forever RLS выключен. При этом роли `anon` и `authenticated` имеют широкие права на эти таблицы, включая SELECT/INSERT/UPDATE/DELETE и TRUNCATE. Это критическая конфигурация: API-ключ приложения публичный, поэтому отсутствие RLS нельзя считать безопасным. Для этих таблиц необходимо срочно спроектировать и проверить политики доступа по участию в группе и авторству реакции/сообщения.

### Дополнительный критический риск: общая таблица profiles

В этой же базе есть таблица `public.profiles`, которую клиент Forever использует для чтения `is_admin`. Таблица содержит также профильные и административные поля, включая `is_banned` и `ban_reason`.

Фактическое состояние:
- RLS выключен;
- для `anon` и `authenticated` выданы широкие права, включая UPDATE и DELETE;
- Advisor отмечает это как ошибку безопасности.

Это потенциально позволяет неавторизованным клиентам менять данные профилей, в том числе административный флаг. Однако `profiles` — общая таблица базы, на неё ссылаются другие приложения/таблицы. Нельзя просто включить RLS или отозвать права без проверки зависимостей: это может сломать другие проекты.

### Другие результаты Advisor

- Публичные `SECURITY DEFINER` RPC-функции: `handle_new_user()` и `rkc_leaderboard()`. Нужно проверить назначение и ограничить EXECUTE для функций, которые не должны быть публичными.
- У `handle_new_user()` изменяемый `search_path`.
- Защита от скомпрометированных паролей в Supabase Auth отключена.
- Найдены 15 внешних ключей без покрывающих индексов и 19 RLS-политик с неоптимальной повторной оценкой auth-функций.
- Есть дублирующиеся permissive-политики на `forever_profiles` и `forever_channel_members`.

### Важное уточнение по исходному аудиту

Первоначально SQL-схемы не нашлось в GitHub, поэтому состояние базы было неизвестно. Теперь проверка реального проекта подтвердила, что backend существует и доступен. Первоначальный вывод об отсутствии схемы в репозитории остаётся верным, но теперь известна фактическая структура удалённой базы.

### Рекомендуемый следующий шаг

До любых изменений нужно подготовить отдельный план исправления RLS:
1. Сначала определить, какие другие приложения используют `public.profiles`, и восстановить их ожидаемую модель доступа.
2. Защитить `forever_groups`, `forever_group_members`, `forever_group_messages`, `forever_reactions` политиками, соответствующими членству и авторству.
3. Пересмотреть источник административных полномочий: нельзя доверять редактируемому клиентом полю или открытой таблице.
4. Проверить RPC-функции и их EXECUTE grants.
5. Только после согласования выполнить изменения в контролируемой миграции и повторно запустить Security Advisor.

**Никаких изменений в Supabase не выполнялось.** Исправление общей таблицы `profiles` особенно нельзя проводить автоматически, пока не выяснены её потребители.
